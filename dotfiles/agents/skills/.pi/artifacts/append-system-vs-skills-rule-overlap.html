C. APPEND-only — nothing in skills, or actively at odds

# APPEND rule Status in skills Note
C1 §5 emit via artifact tool (localhost server, .pi/artifacts/, --bg/--fg CSS vars, no <html> boilerplate, Chart.js container rules) Contradicted. Every HTML-producing skill writes a standalone single file with inline CSS/JS, zero network fetch, dark mode by default, to ./artifacts/ or ./docs/, then xdg-opens it: make-html-aron, grill-me-aron (template shell, must preserve its CSS), make-prototype-aron ("standalone .html, inline CSS + JS"), research-aron, teach Two rendering doctrines. Skills need portable files (user opens, prints, ships them); APPEND assumes the pi artifact server + injected shell. Pick per-output-type, or scope §5 to "ad-hoc reports only, not skill deliverables".
C2 §1 "If uncertain, ask" / "present interpretations, don't pick silently" / "If something is unclear, stop" Contradicted after the autonomy boundary. orchestration.md: "Implementation phase — Zero user question except hard stop"; make-aron anti-pattern: "Ask user anything after implementation started"; roles: "Zero user question" (impl-worker, reviewer, scout, ticket-writer) Not a real conflict if §1 is read as plan-phase-only — but APPEND never says that. Add the phase qualifier to §1.
C3 §2 "No error handling for impossible scenarios" No skill echoes it; make-skill-aron requires the opposite shape for skill text ("every step imperative with a failure branch") Different objects (runtime code vs procedure docs). Harmless, worth not confusing.
C4 §1 "If a simpler approach exists, say so. Push back when warranted." Absent everywhere. Closest is reviewer ("style taste → not a finding") which suppresses opinion Genuinely APPEND-only. Keep.
C5 §3 "If you notice unrelated dead code, mention it — don't delete it" Skills have the drop-and-log-residual-risk analogue (impl-worker, orchestration.md) but never the "mention dead code" case APPEND-only refinement.
C6 §2 "If you write 200 lines and it could be 50, rewrite it" Absent — skills never bound implementation size APPEND-only.

D. What to do with it

  1. Promote to APPEND (true globals, currently skill-local, cheap to state): B2 evidence bar, B8 git append-only, B9 secrets, B11 never run rebuild/system switch, B15 destructive-cleanup guardrails, B19 irreversible-write consent. These are safety rules that should not depend on a skill being loaded.
  2. Fix C2 first — one clause in §1: "Plan phase: ask. Implementation phase (plan confirmed): zero questions, safest in-scope default + logged assumption." Right now the global file and every orchestration skill give opposite instructions.
  3. Scope C1 — §5 covers ad-hoc reports; skill-authored HTML deliverables stay standalone single-file + xdg-open. Say which wins, in both places.
  4. Leave in skills, don't promote: B3 checkboxes, B4 tiers, B5 role-by-path, B6 paths, B12 self-contained tickets, B13 spec ladder, B17 report shapes, B18 caller override, B20 read scope — these only apply when an orchestration skill is running, and they cost context in every unrelated session.
  5. Deduplicate A1–A6 only if you want a shorter APPEND — the skill copies are stricter and load-bearing; the APPEND copies are the fallback for sessions with no skill loaded. Duplication here is deliberate and worth keeping.
  6. B7 caveman is declared "active by default" via ~/.claude/CLAUDE.md — Claude-only. Pi gets it only when a skill links it. Move the toggle line into APPEND if you want it harness-wide.
