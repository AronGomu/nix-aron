1. plan-red-team — adopt. Closes a genuine hole.

make-plan-v2 step 6 already reviews. It is not the same review.

World closed — ticket set vs itself open — plan vs real repo + reality

make-plan-v2 has zero coverage of the right column. Nothing in the skill asks "does this already exist" or "who consumes the thing T3 renames". Ticket-writer children inspect the repo, but each sees one ticket — no one attacks the decomposition as a whole against the code.

Place it at step 4.5, not after step 6

Red-team the index order table right after step 4, before spawning N Opus-xhigh writers.

  • KILL / MERGE verdicts delete rows → each deleted row is one xhigh child never spawned. The gate pays for itself in the most expensive phase.
  • Ordering verdicts (persistence → contracts → producers → consumers) are decomposition-level, i.e. exactly what step 4 emits.
  • Step 6 stays where it is. Two gates, two phases, no overlap.

Honest limitation: at 4.5 there are no ticket bodies, so material is thin. Feed it index + your exploration notes + repo root; scope verdicts per order-table row. Deep per-item attack needs bodies → optional second pass after step 5, gated on production risk only.

Trim before porting

Upstream's 13-step sequence + 8 cross-cutting checks assumes a production web service. On a 4-ticket local plan it manufactures work — and upstream itself says "Do not manufacture risks merely to fill the matrix", which an LLM handed a matrix will do anyway.

Keep:

  • verdict vocab SURVIVES | AMEND | KILL | BLOCKED + MERGE — sharper than reviewer.md's blocker/should-fix/note for plan items, because KILL/MERGE change the ticket count
  • evidence rule: AMEND/KILL/BLOCKED need file:line or cmd output; unverifiable → UNVERIFIED
  • "attack performed" field — forces the reviewer to state what could have disproved the item
  • Never turn an implementation preference into a kill
  • Never recommend queues/caches/microservices without evidence the simpler design misses a requirement — matches B4/C1

Cut or gate: the 8-row cross-cutting matrix → run only on risk signal (data migration · authz · external API · multi-subsystem · >6 tickets · prod deploy). No signal → skip, log skip under ## Assumptions. Greenfield has no code to attack; degrade to architecture + ordering checks and say so.

2. crud-surface-mapper — steal the bug class, drop the rg patterns

Real value = one sentence: a change to an entity must ship to every write surface (fan-out) and stay compatible with every read surface (fan-in). Bug class: field added to edit dialog, missing from create dialog.

That is a decomposition-completeness concern → belongs in make-plan, because an incomplete ticket set is a planner defect the impl worker will not rescue (v1 line: "the implementer runs at standard. It will not rescue a vague ticket.").

Two rules genuinely worth keeping, both stack-agnostic:

  • seed / migration surfaces count — "what happens to rows created before this commit?"
  • a shared consumer gaining a required field needs a named producer on every mounting path

Do not port: pgTable(, db.insert(, createServerFn, Drizzle/TanStack greps. Rots the moment the plan is not that stack.

Form: entry in a new _shared/probes.md, dispatched via the existing scout role, triggered only when a ticket adds or changes a field/behavior on an existing entity. Output lands in that ticket's ## Inputs and ## Impl steps.

3. runtime-contract-tracer — best value per line of the three

The 4-link shape trigger → dispatch → receive → observe is a ready-made ## Interface contract skeleton for any integration ticket, and it is level 5 as-is (make-plan-v2 "Spec level" section demands exactly that).

Two things it forces that make-plan-v2 currently never mentions:

  • silent-failure swallow sites — || true, empty catch {}, >/dev/null 2>&1, .then() with no .catch → belongs in the ticket's ## Validation, since a test that passes because the error was swallowed is the failure mode TDD does not catch
  • the observe link — no observation point = a ticket whose "done" is unprovable. Directly serves E2 (claim ≠ done) and the skill's "Maximize building deterministic tests and validations"

Form: ~10 L template fragment in the ticket template ("integration ticket → contract must name all 4 links; missing link → MISSING, not guessed") + scout brief for when the plan touches an existing integration.

Also worth lifting: Never trust a .d.ts or README for library behavior — cite installed source. That is F1/F3 with teeth, and ticket-writer.md says "by inspection, never memory" without naming this specific cheat.

4. ui-pattern-inspector — weakest fit, still one line worth having

Narrowest and most stack-bound (Radix/shadcn/Cmd+Enter/<Kbd>). Concrete table rots fastest.

But the underlying principle generalises past UI and matches the skill's own granularity bar — "any choice with more than one reasonable answer → you decide it here":

New instance of a recurring family (modal, CLI subcommand, API endpoint, migration, test file) → inventory 2–3 existing siblings, write the convention into the ticket as a decision. "Match app conventions" is not a decision.

Plus NEVER recommend a primitive the project doesn't already use — a D3 restatement (match existing style even when you'd do it differently).

Form: one bullet in the granularity bar + a short scout brief. Do not bundle the inventory table.
